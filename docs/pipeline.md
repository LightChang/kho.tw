## 1. 指令

```

pnpm run pipeline    同上但不建站
pnpm run ingest      只抓到期的來源        transform/scheduler.mjs

pnpm run health      來源筆數異常檢查
pnpm run cluster     跨來源分群
pnpm run relations   課程 → 場館
pnpm run emit        投影、前端索引、統計
pnpm run site        產生 dist/ 靜態網站（astro build）
pnpm run dev         Astro 開發伺服器（KHO_LIMIT=N 只產前 N 門課程頁）
pnpm test            設計系統守門：最小字級 18px、只用 token 色、文字不用 --text-muted
pnpm run sync:tokens  從統一設計系統同步 src/styles/tokens.css
pnpm run ingest:due  只列出誰到期，不抓
```

排程邏輯在程式裡，不在觸發器裡。外部只需要「每小時醒來一次」跑 `pnpm run ingest`。
`scheduler.mjs` 退出碼：`0` 有來源變動（值得往下跑）、`2` 全部沒變（可以直接結束）、`1` 例外。

## 3. 下次抓取時間怎麼決定

宣告值只當起點，實際間隔由「這次內容有沒有變」調整。四類節奏見 `ingest/CONTRACT.md` §3：

| kind | 初始 | min | max |
|---|---|---|---|
| `course-live` | 6h | 3h | 24h |
| `course-archive` | 7d | 3d | 14d |
| `registry` | 14d | 7d | 30d |
| `opendata-monthly` | 3d | 1d | 7d |

```
有變 → interval ÷ 2，夾在 [min, max] 內
沒變 → min(max, interval × 1.5)
失敗 → interval 不變，累積 consecutiveFailures
連續 10 次沒變 → 允許突破 max，最多沉到 30 天
一旦又有變動 → 立刻夾回 [min, max]
```

報名季（`cadence.boostMonths`）初始間隔與下限減半：社大 1、2、7、8 月；
`moe-cc-courses` 用 3、4、9、10 月，因為它是開課後才補登。

同一輪的抓取依 `meta.homepage` 網域分組，同網域序列執行、間隔 2 秒，不同網域併行上限 4。

### 看到課程數變少，先驗不變量再下結論

`moe-cc-detail` 是增量抓取，每跑完一輪、合併就多一批，**課程總數會跟著往下走**——
這是橋接效果不是掉資料。那支來源的記錄同時握有 `internal_course_code`（對得上臺北市聯網的
1.0 規則）與課名時段（對得上教育部列表層的 0.9 規則），於是把原本分開的兩個群接成一群，
群數因此減少。今晚三次快照：

| | 4,000 筆 | 8,000 筆 | 12,000 筆 | 13,010 筆（全）|
|---|---|---|---|---|
| 課程數 | 33,703 | 33,580 | 33,420 | 33,315 |
| 跨來源合併群 | 7,188 | — | 12,863 | 13,767 |
| 1 個來源的群 | 26,359 | 23,331 | 20,404 | 19,396 |
| 3 個來源的群 | 205 | 1,415 | 2,653 | 2,653 |
| 1.0 規則命中 | 300 | — | 4,713 | 4,717 |
| 描述覆蓋 | 36.4% | 45.1% | 53.6% | 56.5% |

**要分辨「合併」與「掉資料」，看三件事**：

1. **`clusters` 的行數必須等於 `courses` 的行數**（一群＝一門課）。這是最硬的不變量，
   兩者對不上就是真的出事了。
2. **`bySourceCount` 的重心要往右移**：1 個來源的群變少、2 個以上的變多。
   若 1 個來源的群沒減少而總數卻降了，那就不是合併。
3. **座標與行政區的百分比幾乎不動**（今晚三輪是 59.4→59.3→59.1%、70.3→70.2→70.1%）。
   合併吸收掉的課本來就有座標，所以分子分母同步減少、比例只掉 0.1 個百分點；
   若比例明顯下滑，代表掉的是有座標的那批，要查。

`openNow` 也會跟著少（8,841 → 8,840），那是兩門原本各自獨立且都在招生的課被併成一門。
首頁主打這個數字，看到它變動時用上面三項驗一次就知道是不是正常。

這些數字每輪都會小幅變動，不必追著改：同一天稍晚重抓，`cc-shared-platform` 就從 4,077 掉到
3,973（那五個間歇性 503 的社大主機又掛了一個）、`taiwanjobs` 2,396 → 2,368、`xuanen-centers`
3,859 → 3,853，跨來源合併也跟著從 3,191 回到 3,100。健康檢查的門檻是掉幅 50%，這種等級的
浮動屬正常呼吸。

分群規則與實測：

| 規則 | confidence | 命中 |
|---|---|---|
| 校名＋期別＋校內課程代碼 | 1.0 | 4,717 |
| 校名＋課程代碼（來源缺期別時） | 0.95 | 2,042 |
| 校名＋期別＋課名＋星期＋開始時刻 | 0.9 | 23,559 |
| 校名＋期別＋課名＋教師（＋星期） | 0.8–0.85 | 772 |

1.0 規則的命中在 2026-09-13 從 300 跳到 4,717，是因為接了 `moe-cc-detail`——
`internal_course_code` 只有詳情端點才給，在那之前教育部這 13,010 門課一個代碼都沒有，
這條規則對全站最大的來源從來沒成立過。

**`normSchool()` 回空字串時，那所學校的課一條鍵都產生不出來。** 上面每條規則都要求
`school` 非空，而 `normSchool()` 先剝縣市前綴、再剝「社區大學／社大」後綴——
「澎湖縣社區大學」就這樣被剝成空字串。實測澎湖 137、花蓮 122、臺東 105 共 364 筆 L1
來源數清一色是 1，永遠各自 singleton。修法是剝完為空時退回「剝後綴、再去掉結尾的縣／市」，
讓「澎湖縣社區大學」與簡稱「澎湖社大」都收斂成「澎湖」（全站碰撞檢查只撞出這三組同校異名）。

順帶查清楚但**不該改**的一件事：花蓮 `hualien-cc` 72 門、澎湖 `penghu-cc-portal` 49 門
仍然沒跟 moe 兩支合併，這是正確的。`SEASON` 對照裡 1 = spring，moe 這批 `1151` 是
115 年**春季**（`date_begin` 實際是 3 月），而那兩支是**秋季班**。課名與教師相同只因為
社大同一門課春秋都開，是不同期的不同班。兩支的 `term` 也都已解析出 `year`+`season`，
`termKey` 本來就對得上，不是正規化缺陷——別再為了「提高合併率」去動它。

課程代碼取 `schoolCourseCode`、`centerCourseCode`、`taiwanjobs` 三個鍵。少了第三個，
職訓類的跨來源分群從頭到尾不會觸發——2026-09-13 補上後，taiwanjobs 與兩支 mol
開放資料合併了 66 筆（6060 的 64 筆、6614 的 2 筆），與實測重疊數完全相符。

兩個防呆：雙方都有課程代碼且不同 → 不合併；同來源、雙方都沒有代碼 → 弱規則不合併。
沒有這兩條時，林口運動中心「運動按摩」的 51 個班次會被合成一門課。

場館解析方式：名錄比對（門牌）11,427、名錄比對（名稱）4,773、有座標的門牌 5,272、
只有門牌 469、只有場地名 4,253、完全沒有地點 7,121（懸空邊，課程頁照常顯示文字，
只是不連到場館頁）；另有 398 條走「名錄沒座標時回頭查 geocoded」補上。

**行政區改用對照表反推，不用 regex 猜**（`overrides/districts.json`，367 個行政區，
由四支政府名錄自帶的 `city`+`district` 產生）。來源多半只給縣市，但地址字串裡本來就寫著
行政區（「臺中市西區五權路2之3號」的 `district` 是 null，可是「西區」就在地址裡）。
比對「該縣市底下真實存在的行政區、取最長命中」，場館 694 → 1,912、課程 50.9% → 70.3%。
不可以用 `/^(縣市)([一-龥]{1,3}?[區鄉鎮市])/` 直接抓：非貪婪的 `[區鄉鎮市]` 會先吃到
「前鎮區」的「鎮」、抓成「前鎮」，578 筆對照組有 6 筆栽在這裡。

**接名錄類來源時，量淨效果要用課程層、不可以用場館 id**（詳見 CONTRACT §4）。
對到名錄之後場館 id 本來就會變（`hash8(門牌)` → `hash8(名錄來源|記錄)`），
拿「舊 id 還在不在、有沒有 lat」當判準會得到一堆假警報——接學校名錄時我先用了這個錯判準，
報出「36 個場館、152 門課失去座標」，逐一追查才發現**一門課都沒掉**，那些門牌全被學校名錄
接手、lat 與原值一模一樣，只是換了 id 和一個更好的名字（「桃園市桃園區三民路3段22號」
變成「市立成功國小」）。
懸空邊占 21%，主要來自兩個沒有地址欄位的來源：桃園聯網 1,206 門（列表層沒地址）
與臺南七校 1,160 門。這類課程照樣看得到、連得回原始頁面，只是地圖上找不到。

**名稱比對必須同縣市**：名錄裡同名但不同地址的場館有 750 組——「田徑場」279 個、
「校本部」104 個、「籃球場館」102 個。純名稱比對會把不同縣市的課串到同一個場館上，
實測臺東的課掛進「澎湖縣社區大學」、臺北的課掛進臺中「太平國小」。現在兩邊都知道縣市時
就必須一致，只有其中一邊缺縣市才容許比對（否則覆蓋率退步太多）。門牌比對不受此限制，
因為門牌本身就帶縣市。加上這條之後，跨縣市的名稱比對從 283 條降到 0。

## 5. 健康檢查為什麼不用 seh.tw 的 30% 規則

課程是期別制，學期中穩定、期末歸零、開報名日暴增，30% 掉幅會天天誤報。改成：
掛零→失敗；掉幅 >50% 且不在期別切換窗口→失敗；在窗口內→只警告；與去年同期比掉 >50%→失敗。
窗口：社大類 1、2、7、8 月；運動中心是雙月期別，取每個單數月的 1–10 日。

## 6. 結構化資料（JSON-LD）

`site/jsonld.mjs` 產生，`site/validate-jsonld.mjs` 離線驗證（`pnpm run validate`）。

**先查證再實作**：Google 的「Course info」複合式搜尋結果已淘汰（2024-09 列入淘汰計畫、
說明文件已移除），目前仍支援的是 **Course list（課程輪轉介面）**：

- `Course` 必要 `name`、`description`（顯示上限 60 字），建議 `provider`
- 清單頁要 `ItemList.itemListElement` ＋ `ListItem.position` ＋ `ListItem.url`，至少三門課

實際產出：課程頁 33,832 個 `Course`、場館頁 2,385 個 `Place`、彙整頁 3,234 個 `ItemList`
（縣市／主題／類型／可報名各一，其餘全是講師頁——每位講師的課程清單本身就是一個 ItemList）。

其餘屬性照 schema.org 詞彙寫（對複合式結果不加分也不扣分，但對 AEO 與 LLM 取用有用）：
`hasCourseInstance.courseSchedule`（`byDay` 用 DayOfWeek 列舉、`repeatFrequency` 用 ISO 8601
duration、`scheduleTimezone: Asia/Taipei`）、`location`（含 `PostalAddress` 與 `GeoCoordinates`）、
`instructor`、`offers`。

兩個刻意的取捨：

- **`description` 缺的用自己的欄位組一句事實**（主辦、期別、星期時段、起始日、地點），
  因為來源只有 23.5% 有描述，而它是必要屬性。不編造內容，只重述已有資料。
- **`offers.availability` 只對應語意明確的狀態**：招生中→InStock、額滿→SoldOut、
  尚未開放→PreOrder、已截止→OutOfStock、停開→Discontinued。
  「開課中」與「狀態未知」不寫 availability——寧可不宣告，也不宣稱不確定的事。

## 7. 網站與首頁

頁面種類：

```
/                    首頁：滿版一頁（100dvh），橫豎都不可捲；視窗高 ≤660px 或寬 ≤900px 改為「至少滿版、放不下就捲」
/open.html           現在可報名，依縣市分組
/types.html          課程類型索引      /type/<kind>.html
/cities.html         縣市索引          /city/<縣市>.html
/search.html         前端即時搜尋（讀 /index.json，支援 ?q=）
/course/<slug>.html  課程頁：最終值、各來源並排、落選值
/venue/<slug>.html   場館頁
/sitemap.xml         sitemap index，指向五個分檔 sitemap-<群組>-<n>.xml
/robots.txt          全站開放檢索，指向 sitemap.xml 的絕對網址
```

**首頁的四個門各管一個面向，不是四選一**：現在可報名（時效）、學什麼（類型）、
在哪裡（縣市）、搜尋（已知道要找什麼）。中段右側是「快額滿」倒數——名額數字只有
軒恩報名系統與臺中聯網給得出來，是本站少數別處看不到的資訊。

色票**不沿用 seh.tw 的**，但**字級量表直接採用 design-tokens 技能的官方值**
（`~/.claude/skills/design-tokens/typography.md`：xs 18px／sm 20px／base 24px／lg 28px／
xl 32px／2xl 48px／3xl 56px，行高 1.6，最小 18px「無例外」）。使用者是想找課的成人與
樂齡族群，字大與對比本來就是需求。顏色帶語意（招生中綠、額滿紅、尚未開放琥珀、
開課中藍、停開灰），全站一致，OKLCH 並附 hex fallback。

2026-09-14 之前這裡是自訂的偏小量表（xs 15.2px／sm 16.8px／base 18.4px），還有一處
寫死 0.85rem（13.6px），都低於規範下限——而 `--fs-xs` 用在狀態膠囊、次要說明與表格註記上，
正是最該看清楚的地方。

三個檢查器都納入 `pnpm run validate`，`pnpm run build` 收尾會自動跑：JSON-LD 結構驗證、
站內連結驗證、sitemap 與 robots.txt 驗證。第二個抓過三個實際的 404：兩個是可報名頁連到不存在的
「未標示縣市」頁，一個是換 slug 時首頁「快額滿」的資料沒帶到 slug、整批連到
`/course/undefined.html`（畫面上看不出任何異狀，只有檢查器會講）。

### 主題分類的入口：`/topics.html` 與 `/topic/<分類>.html`

站上有**兩套彼此獨立的分類**，兩套都要留：

- **機構類型**（`/types.html`、`/type/<kind>.html`，9 類）：社區大學、運動中心、樂齡中心、
  職業訓練⋯⋯這是「誰開的課」，來自 `provider.kind`。
- **主題分類**（`/topics.html`、`/topic/<分類>.html`，18 類）：語言、運動健身、美術工藝⋯⋯
  這是「學什麼」，來自 `overrides/taxonomy.json`。

主題分類本來只印在課程頁的一列文字上，沒有任何索引頁——使用者想「我要學語言」沒有入口可走。
18 類做出來卻沒有門，等於白做，所以補了索引頁，導覽列也改成
`可報名 / 主題 / 類型 / 縣市 / 搜尋`。首頁是 `bare` 模式、不吃導覽列，版面不受影響。

**推斷來的分類照樣收進分類頁，但每張卡片標「分類依課名判斷」。** 全站 29,947 門已歸類的課裡，
來源自己標的與從課名推斷的大約各半；把推斷的排除掉，多數分類頁會少掉一半以上
（舞蹈 2,545 → 498、音樂戲劇 3,835 → 1,017、旅遊休閒 279 → 33），入口就失去意義。
但推斷是本站的判斷、不是來源講的事實，所以標示出處，分類頁開頭也寫明該類有幾門是推斷的。

### 講師頁：身分怎麼認定

`/teachers.html` ＋ `/teacher/<姓名-單位-短碼>.html`，6,647 頁。回答的是「這位老師還開了哪些課」。

**身分 ＝ 姓名 ＋ 開課單位（含縣市），不是只看姓名。** 來源只給名字、沒有任何識別碼，
分不出「跨校開課的同一人」與「剛好同名的兩人」——8,407 個可用姓名裡有 3,028 個（36%）
出現在兩個以上單位，「鐘婉綺」「陳建志」各有 17 個。**合錯是在頁面上對真實個人做不實陳述，
拆錯只是少一個彙整、每頁內容仍然全是真的**，所以選擇拆。跨校的損失用「站內同名的其他講師頁」
交叉連結補回來，那一區明講可能是同一人、也可能只是同名，不替讀者認定。

單位不能只做字面比對：同一所學校實測有四種寫法（臺北市文山社區大學／台北市文山社區大學／
文山社區大學／文山社大），不折就會把同一個人拆成四頁（實測 685 組、1,420 個身分是規則自己
製造的分裂）。但也不能乾脆丟掉縣市前綴只留「文山社大」——那會把**臺北市文山社區大學與
臺中市文山社區大學兩所不同學校合併**，正是要避免的方向。最後是「縣市留在鍵裡、只折單位名的
寫法差異」，殘餘同單位分裂 685 組 → 0 組。

**只有 2 門課以上才產頁**（1 門 4,241 位／2–5 門 6,068／6 門以上 757）。一門課的講師頁
內容與課程頁完全重複，答不了「還開了哪些課」，卻要多 4,241 頁進 sitemap 搶抓取預算。

姓名雜訊：分隔符切得開的就切，切不開的整筆不認（「佐佐木 滋」是一個人、
「謝進忠 貝雪玲 劉梅英」是三個人，同樣是漢字加空白，切也錯不切也錯）；括號綽號與頭銜剝掉；
集合名詞一律不產頁（「專業師資」278 門、「講師群」51 門）。**只用來源已公開的姓名**，
頁面只放本站收錄的課程，不加任何個人資訊，也不跨單位替人合併身分。

### 門卡數字：撐滿卡片，位數多就自動縮小

`8,841` 這種數字要盡量大，但四張卡的位數不一樣（8,841／9／21／8,727），
給固定字級的話不是小數字太小、就是大數字溢出。做法是讓字級由卡片寬度與位數決定：

```
.door { container-type: inline-size }        卡片自己成為度量單位
.door .n { font-size: clamp(1.125rem, min(100cqw / var(--len) * 1.55, 6vh), 4rem) }
```

`--len` 是數字的字元數（含千分位逗號），由 `src/pages/index.astro` 輸出時一併寫進 style。
CSS 無從得知字串多長，這是唯一不靠 JS 的辦法。

係數 **1.55**：等寬數字每字約 0.62em，`0.62 × 1.62 ≈ 1.004`——用 1.62 會讓數字寬度
剛好等於卡片內寬，一點邊都不留，實測 1024×768 與 390×844 的五位數就是這樣貼齊甚至溢出。
1.55 留約 4% 餘裕；逗號比數字窄，實際還會再鬆一些。

**`min()` 那一項是防爆版用的，不是美觀取捨。** 首頁是滿版一頁，卡片一撐高就爆。
數字同時受兩件事限制、取其小者：`100cqw / --len * 1.55` 管橫向（卡片放得下幾位數），
`6vh` 管縱向（視窗放得下多高）。最短的字串（「9」）最容易吃滿上限，由 `6vh` 擋住。

2026-09-14 之前這裡是「四個斷點各給一個死上限」（4rem／2.8rem／2.4rem／2.1rem）。
那種寫法**必定有縫隙**：斷點之間上限是固定的、容器高度卻隨視窗連續變化，
所以每個斷點的正上方一定有一段區間裝不下——實測 841 差 4px、769 差 2px、761 差 3px，
而 1366×768 破版半年也是同一個病。改成 `6vh` 之後上限自己跟著視窗連動，
四段 media query 全部刪掉。

同一個原則套用在門卡的其餘尺寸上：行高、`gap`、`padding` 也都綁 vh
（例如 `padding-block: clamp(3px, 1.5vh, 20px)`），內容高度就跟著容器一起連續變化。
**字級本身不參與縮放**——18px 是 design-tokens 的下限，「無例外」。

### 地圖與「找我附近的課」：`/map.html`

`src/pages/map.astro` ＋ `dist/venues-map.json`（`src/pages/venues-map.json.js`）（1,782 個點、211 KB）。四個刻意的選擇：

**圖磚用內政部國土測繪中心的臺灣通用電子地圖（EMAP6），不用 OpenStreetMap。**
台灣的路名、門牌與行政界線比 OSM 準；免申請免金鑰；授權是「政府資料開放授權條款－第1版」，
**要求標示出處**，所以頁面底部與地圖右下角都固定標示。端點是標準 XYZ 格式：

```
https://wmts.nlsc.gov.tw/wmts/EMAP6/default/GoogleMapsCompatible/{z}/{y}/{x}
```

2026-09-14 實測：`access-control-allow-origin: *`、回應 40–110ms、無縮放層級限制、
瀏覽器帶 Referer 也不擋（headless 實測 12 塊圖磚全部載入）。
OSM 官方圖磚的使用政策雖然允許「一般人類瀏覽」，但明文建議正式站改用第三方或自架，
而且對台灣的地名精度也不如 NLSC。

**Leaflet 自己放一份在 `/lib/`，不從 CDN 載。** 整站原本零外部連線；接了地圖之後訪客只會
多連 NLSC 圖磚主機一個——那是功能必需，cdnjs 不是。`public/lib/` 放 `leaflet.js`（147 KB）、
`leaflet.css` 與它參考的 5 個 PNG（marker 圖示、圖層切換圖示），Astro 從 `public/` 一併複製到 `dist/`。

**按「場館」聚合，不是按「課程」。** 19,671 門有座標的課只落在 1,782 個地點上，
聚合後資料從 1.3 MB 降到 211 KB，地圖也不會在同一個點疊幾十個標記。
1,782 個點用 canvas renderer 畫 `circleMarker`，實測不需要 markercluster 外掛——
又少一個外部依賴。圓點半徑依課程數但設上限 14px，否則臺北幾個大場館會蓋掉整個臺北。

**精度警語不是客套話。** 這些座標有 635 個來自名錄門牌比對、97 個來自場館名稱比對，
只夠回答「在哪一區」，不夠回答「走路五分鐘會不會到」。所以「找附近」只給**直線距離**、
明講不是步行距離、不做路線規劃、不寫「步行 N 分鐘」。做不到的事不要在介面上暗示做得到。

### 可讀網址（slug）

課程頁與場館頁的檔名、站內連結、canonical 與 sitemap 全部用可讀 slug，不用 id。
規則在 `transform/slug.mjs`，由 `transform/emit.mjs` 配給並記在 `data/slugs.ndjson`，
網站（`src/lib/data.mjs`）只讀不改。

```
/course/飛越拉拉二胡-五權社大-48d29.html    課名（≤20 字）-單位（≤12 字）-短碼（5 碼）
/venue/凡穀創意工作坊-35643.html            場館名（≤20 字）-短碼（5 碼）
```

四個設計點：

- **穩定性靠登記簿，不靠規則**。`data/slugs.ndjson` 是 id → slug 的 append-only 對照，
  **同一個 id 只配給一次**，之後重跑一律讀回原值：課名多一個空白、改標點、甚至整句改寫，
  網址都不動。下架的課保留原行不刪，網址不會被別門課撿去用，來源把課放回來也拿得回原網址。
  規則層的正規化（剝掉 `【11/18開課】` 這種會隨日期變動的前綴、去掉所有標點與空白）
  只是減少「同一件事兩種寫法」的雜訊，真正的保證是登記簿。
  2026-09-13 實測：連跑兩次 `emit`＋`build`，登記簿 SHA-256 未變（新配 0 筆）、
  `dist/` 的 42,460 個檔名集合與七個 sitemap／robots 產出雜湊完全相同。
- **唯一性靠短碼**。同名課程很多（好幾所社大都有「太極拳」）：實測 5,896 組
  「課名-單位」會撞，涉及 15,240 門課，最大一組 81 門。補上短碼後，33,832 個課程 slug、
  2,385 個場館 slug 與 6,832 個講師 slug **大小寫折疊後 100% 唯一**，
  而且全部只用 5 碼就夠，沒有一筆需要加長。
  短碼取自 id（sha256 前 8 碼）的尾 5 碼；撞到才依序加長到 6、7、8 碼，而 id 唯一，所以一定收斂。
  5 碼是權衡：碰撞空間只用在「同課名同單位」這種通常個位數的小群組，網址也只多 6 個字元。
- **長度**。課名 20 字、單位 12 字（課名 p90 是 16 字、單位 p90 是 11 字，多數根本不會被截）。
  中文百分比編碼後一個字 9 個字元，所以字數就是網址長度：全站編碼後中位數 115 字元、
  最長的一個 295 字元（39 字），完整網址 322 字元。
  單位名稱先砍掉不能辨識的部分再截：`財團法人`／`社團法人`（350 個單位、1,168 門課的名稱
  以它開頭）、縣市前綴，並把「社區大學」縮成「社大」、「國民運動中心」縮成「運動中心」，
  額度才花在真正分得出是哪一家的字上——否則截出來會是「財團法人臺北市華夏婦女文」。
- **檔案系統安全用白名單**，不逐個列黑名單。只留 Unicode 文字與數字（`\p{L}\p{N}`），
  其餘一律拿掉——這一刀同時解決 `/`、`:`、`?`、`*`、`"`、`<`、`>`、`|`、`\`、控制字元、
  前後空白與句點結尾（實測課名裡這些字元全部出現過）。字串一律 NFC；
  唯一性比對再折一次大小寫，因為 macOS 檔案系統大小寫不敏感，
  `ZUMBA-…` 與 `zumba-…` 會互相覆蓋成同一個檔案。

兩個連帶改動，改首頁或搜尋頁前要知道：`public/index.json` 第 0 欄從 id 換成 slug
（前端沒有 id → slug 的對照表，放 id 就連不出去）；`public/home.json` 的 `almostFull[].id`
放的是**百分比編碼後的 slug**，因為首頁（`src/pages/index.astro`）直接把它串成 `/course/<id>.html` 且不再編碼，
而首頁版面是量測驗收過的、不動它——真正的課程 id 另外放在 `courseId`。

**本站尚未上線，所以這次換網址不做轉址**：沒有外部連結、沒有搜尋引擎已收錄的網址，
舊的 `/course/crs_00048d29.html` 直接消失即可。這個前提只成立這一次——
**上線之後再改 slug 規則，就必須連同 301 轉址表一起做**（登記簿裡有舊值，
產生對照表不難，但那時候是必做，不是可省）。

### sitemap 與 robots.txt

`site/sitemap.mjs` 產生，由 `src/lib/sitemap-integration.mjs` 在 build 完成後呼叫（條目由資料推出，
再逐一確認檔案在 `dist/` 裡，所以 `KHO_LIMIT` 開發模式不會產出指向不存在檔案的網址），`site/check-sitemap.mjs` 驗證（`pnpm run validate`，單跑 `pnpm run sitemap`）。

2026-09-13 實跑（可讀 slug、29 支來源、主題分類 19 頁與講師頁 6,647 頁之後）：42,460 個 URL、五個分檔，與 `dist/` 的 42,460 個 `.html`
一對一。中文 slug 編碼後比原本的 `crs_<hash>` 長，所以分檔的位元組數也跟著變大。

| 檔案 | URL 數 | 未壓縮 |
|---|---|---|
| `sitemap-pages-1.xml` | 55 | 0.00 MB |
| `sitemap-courses-1.xml` | 20,000 | 5.44 MB |
| `sitemap-courses-2.xml` | 13,315 | 3.63 MB |
| `sitemap-teachers-1.xml` | 6,646 | 1.48 MB |
| `sitemap-venues-1.xml` | 2,444 | 0.57 MB |

三個取捨（理由也寫在 `site/sitemap.mjs` 開頭）：

- **一開始就做 sitemap index，不是等超過上限再改**。協定上限是單檔 50,000 個 URL、未壓縮
  50 MB，現在都還沒到，但來源才接了 11/41 個，課程數只會再長；等超過才改結構會連帶動到
  已經送給搜尋引擎的 sitemap 網址。每檔上限訂 20,000（協定的四成），留成長空間。
- **`lastmod` 用資料的日期，不是 build 當下的時間**。課程取 `sources[].lastVerifiedAt` 的最大值，
  彙整頁取它收錄的課程的最大值，首頁取 `public/home.json` 的 `updatedAt`。寫 `new Date()` 的話
  sitemap 的 git diff 每次都整份變，看不出哪些課真的更新了，對搜尋引擎也是狼來了。
  同一份資料連跑兩次 build，六個產出檔的 SHA-256 完全相同（2026-09-13 實測；2026-09-15 移植 Astro 後與舊產生器逐檔比對，六個 sitemap 檔與 robots.txt 位元組相同）。
- **停開與已截止的課仍然收錄**——這些頁面對「這門課還在不在」是有答案的，抽掉只會變成 404。
  但它們不會再變動，所以 `priority` 壓低、`changefreq` 拉長，把抓取預算讓給招生中的課：

| 狀態 | priority | changefreq |
|---|---|---|
| 招生中 `open` | 0.9 | daily |
| 尚未開放 `upcoming` | 0.7 | weekly |
| 額滿 `full`／開課中 `running` | 0.6 | weekly |
| 狀態未知 `unknown` | 0.5 | weekly |
| 已截止 `closed` | 0.3 | monthly |
| 停開 `cancelled` | 0.2 | monthly |

中文路徑一律百分比編碼：`/city/臺北市.html` 在 sitemap 裡是
`https://kho.tw/city/%E8%87%BA%E5%8C%97%E5%B8%82.html`。課程頁與場館頁換成中文 slug 之後
同一套規則照用，`site/jsonld.mjs` 的 `pageUrl()` 與 `site/sitemap.mjs` 的 `toLoc()`
必須編出一樣的結果，否則 canonical 與 sitemap 會對不起來（`check-sitemap.mjs` 第 4 項就是驗這個）。

`robots.txt` 允許全站檢索並指向 sitemap 的絕對網址。**`/index.json`（3.6 MB、33,832 筆的前端
搜尋索引）刻意不擋**：`/search.html` 是純前端，整頁內容靠 `fetch('/index.json')` 生出來，擋掉它
爬蟲算繪時就拿不到資料、搜尋頁變空殼——Google 明確建議不要用 robots.txt 擋算繪需要的資源。
它也不在 sitemap 裡（sitemap 只收 HTML 頁面），本站不主動推它，內容本身也已經有 33,832 個
課程頁作為正式可索引的版本。真要避免這個 JSON 自己被列成搜尋結果，正解是回
`X-Robots-Tag: noindex` 標頭，那是部署端的設定（本 repo 目前沒有任何主機設定檔），
robots.txt 管不到，不在這裡假裝管得到。

`site/check-sitemap.mjs` 驗十件事：XML well-formed（檢查器是自己寫的，不靠套件，
只驗這份產出會出錯的地方：標籤配對、單一根節點、跳脫）、index 指到的分檔都存在且根節點是
`urlset`、每個 `<loc>` 是 `https://kho.tw` 開頭的絕對網址、百分比編碼與產生時一致（這條抓得到
「沒編碼」與「編碼兩次」）、解碼後在 `dist/` 真的有對應檔案、全站沒有重複 URL、未超過每檔
20,000 個 URL／50 MB、`lastmod`／`changefreq`／`priority` 格式合法、`dist/` 每個 `.html` 都被收錄
且只出現一次、`robots.txt` 存在且 `Sitemap:` 指向存在的檔案。

### 滿版一頁是量出來的，不是宣告出來的

`height:100dvh` ＋ `overflow:hidden` 只保證「不會出現捲軸」，塞不下時是**把內容裁掉**，
比捲動更糟且不會有任何錯誤訊息。所以要用無頭瀏覽器實際量（腳本：`site/check-layout.mjs`）：

```
頁面層級   scrollWidth/scrollHeight vs clientWidth/clientHeight（兩軸都不可溢出）
區塊層級   .ask/.doors/.hot/.foot 的 bottom 不可超出視窗
重疊檢查   相鄰區塊的垂直範圍不可交疊（同一欄時）
內容層級   每個容器 scrollHeight <= clientHeight（這才抓得到「字被切一半」）
```

**重疊檢查是補上去的，因為前三項會漏。** 390×844 曾經出現底部的「縣市／臺北市…」
整行壓在下排兩張門卡上，但前三項全部通過——每個框確實都還在 844px 內，
問題出在中段被 `minmax(0,1fr)` 壓縮後，卡片內容溢出自己的格子去和底部重疊。
數字說沒事、截圖一看就知道壞了。**版面改動一定要同時看截圖，不能只看量測值。**

同一個錯誤在 1366×600 也發生過一次：門卡內容 328px 被壓進 230px 的格子，
底部「縣市／類型」兩行蓋住「在哪裡」「搜尋」兩張卡的數字。方向是對的——矮視窗要
縮小門卡內容本身，而不是讓它溢出；但當時的做法是 `max-height:760/660/560px` 三段瘦身，
2026-09-14 已改成隨 vh 連續縮放（見「門卡數字」一節），那三個斷點已經不存在。

`site/check-layout.mjs` 是**手動腳本**：它匯出一段檢查用的 JS 字串，貼進瀏覽器主控台或
透過瀏覽器驅動執行。要真的量版面就需要瀏覽器，專案不為了它裝 playwright，
所以不做成 `pnpm run`——與其擺一個跑不起來的指令，不如寫清楚它怎麼用。

**2026-09-13 那一輪的教訓（數值已被 09-14 改版取代，但成因要記住）**：當時固定驗
1440×900／1366×600／1024×768／390×844 四個常見解析度，**漏了 1366×768，而破版就在那一格**
——寬 1366 > 1100 所以說明文字 `.d` 還在、高 768 > 760 所以門卡瘦身不生效，
四張卡片內容 189px 塞進 185px 的容器，各溢出 4px。當時的修法是把瘦身斷點從 760 放寬到 800，
也就是把破版區間往上挪、而不是消掉它——所以 2026-09-14 字級一改，
841／769／761／721 又各差 2–4px，同一個病換個位置再犯一次。

**2026-09-14 改版後實測 38 個尺寸全過**（Chromium headless，尺寸取法見下方「怎麼挑驗證尺寸」）。

放不下才捲。`site/check-layout.mjs` 的「允許直捲」條件同步改成 `vh <= 660 || vw <= 900`，
修改後同一組 189 格加 10 個桌面尺寸全數通過。

**驗這一輪時踩到三個工具問題，記下來免得下次又被騙**：

1. playwright 會間歇性停在 `about:blank`（`navigate` 回報成功，但 `outerHTML.length` 只有 39）。
   空白頁會讓版面檢查回傳 `pass: true`——沒有內容當然不溢出。**這個假通過最危險**，
   所以檢查腳本開頭要加 `if (outerHTML.length < 500) return {BROKEN:true}`。
2. **`playwright_navigate` 的 `width`/`height` 會被忽略**：指定 1366×768，量到的卻是
   1440×900（沿用前一次的視窗）。換尺寸要用 `playwright_resize`，而且腳本裡必須核對
   `innerWidth/innerHeight`，否則會拿 A 尺寸的 pass 當成 B 尺寸驗過了。
3. 兩條路都不通時，我試過「解析 CSS 算出各尺寸的字級上限」當備援，**連寫兩版都是錯的**
   （正則切 media 區塊會把宣告掛到錯誤的條件上，算出 1440×900 是 2.1rem，與實測的 4rem
   直接矛盾）。手寫正則解析 CSS 層疊不可靠，不要再走這條路——工具壞掉就誠實說沒驗到。

**怎麼挑驗證尺寸。** 舊結論是「挑落在斷點兩側的尺寸」，那是症狀處理——2026-09-14 證明
**根因是階梯式設計本身**：只要內容高度靠 media query 分段寫死，斷點正上方就必定有縫隙，
補完一個又長出下一個。正解是讓內容隨 vh 連續縮放，縫隙根本不存在（見「門卡數字」一節）。

現在的驗法是掃一個範圍、不是挑幾個點：1440 寬掃 940→460 共 31 個高度（含每個殘存斷點的
兩側），再加 1366×768／1280×800／1024×768／390×844／414×896／360×640／320×568。
殘存的高度斷點只剩四個：`720px`（門卡說明退場）、`660px`（改為可捲）、
`640px`（快額滿副標退場）、`560px`（快額滿整塊退場——容器只剩 2 列高度，
一列的「快額滿」沒有資訊價值，不如把空間讓給門卡）。

**量 38 個尺寸不要用 `playwright_resize` 逐一切換**（一次只能一個，而且不會重新載入頁面）。
改成在同一頁裡建 iframe、逐一設定寬高載入，一次 `evaluate` 就量完。用之前先拿一個已知
尺寸當對照組——iframe 量 1440×900 必須重現直接量到的數字，對不上就別用這個量法。
每個 iframe 的 `src` 都要加 cache-buster，否則會量到重建前的舊頁面；內頁吃外部 `/style.css`，
HTML 的 cache-buster 擋不住樣式表快取，要另外讀 computed 值確認（例如 `body` 是不是 24px）。

**iframe 量法有一個前提：主分頁本身必須真的停在 `http://127.0.0.1:PORT/` 上。**
playwright 的主分頁會間歇性掉回 `about:blank`（見下方「瀏覽器驅動整個壞掉時怎麼辦」），
一旦掉了，iframe 量法會用兩種不同的方式壞掉，而且都**不是版面的問題**：

- `src` 寫 `/index.html` 這種相對路徑時，是拿主分頁的 `location` 當基底解析的，
  `about:blank` 不能當基底，於是什麼都載不到。
- 改寫成絕對網址也救不了：`about:blank` 是 opaque origin，從它建立的 iframe 去載
  `http://127.0.0.1:PORT/...` 算**跨來源**，`contentDocument` 直接是 `null`。

所以絕對網址該用（省掉第一種），但它**不是免疫**，真正的前提是同源。
分辨方法：先 `curl` 確認 server 還活著、`dist/index.html` 內容正常，再在主分頁讀 `location.href`
——是 `about:blank` 就是環境掉了。**這種時候不要去改 CSS**：38 個尺寸同時失敗幾乎都是環境問題，
真正的破版是零星的。

**而且 `navigate` 回報成功不代表它生效**：實測連續兩次回報「Navigated to ...」，
`location.href` 仍是 `about:blank`。navigate 之後一定要再讀一次 `location` 確認；
還是不動就 `playwright_close` 關掉瀏覽器重開，不要在同一條路上反覆重試。

重驗窄視窗不是形式：底部「類型」那排在接了圖書館來源後從 5 項變成 6 項，
而手機版的 `.foot ul` 解除了高度上限、改成依內容撐開——多一項就有可能把底部撐高、
反過來壓縮中段的門卡。2026-09-14 實測 390×844 各留 2 項、門卡 96／95 沒有溢出；
1366×600 這種矮視窗現在走可捲模式，底部依內容撐開、不再靠裁切控制高度
（可捲模式下**不可以**再給 `.foot ul` 設高度上限，理由見下方規則最後一條）。

**檢查項目後來補了兩條，都是被實際漏掉的問題逼出來的**：

- **連結不可以是 `undefined`**：換 slug 時「快額滿」整批連到 `/course/undefined.html`，
  版面量測完全正常、畫面也看不出異狀，是連結檢查抓出來的。
- **元素必須真的存在**：有一次量測回報 `pass: true`，但頁面根本是空的。
  原本的判定只看「有沒有溢出或重疊」，空白頁當然全過。現在 `pass` 多要求一組
  `missing` 為空：`.home` 在、門卡剛好四張、`.tally` 在、`body` 文字至少 200 字。
  **刻意不要求「快額滿至少一列」**——那一塊在 ≤900px 寬與 ≤560px 高是刻意整塊隱藏的，
  拿它當必要條件會把正常的窄視窗判成失敗。
  （2026-09-14 補記：這段先前描述的檢查其實沒有寫進 `check-layout.mjs`，
  文件宣稱擋得住、程式碼實際擋不住，比單純過時更糟。現在是照著程式碼重寫的。）

**2026-09-13 補記：瀏覽器驅動整個壞掉時怎麼辦。** 改門卡數字那一輪，`navigate` 每次都
回報成功，量測卻全部歸零（`doors: 0`、`bodyText: 0`），截圖全白。查下去是瀏覽器停在
`about:blank`、整份文件只有 39 個字元，`file://` 與本機 HTTP 都一樣，而同一個網址用
`curl` 拿得到 23KB。連續五次都如此，等於視覺驗證這條路斷了。

這種時候**不要繼續重試，也不要宣稱版面驗過**。那一輪的版面結論是改用計算核對的：
把產出 CSS 裡的 `clamp()` 參數解析出來（注意 `calc(100cqw / var(--len,3) * 1.55)`
本身含逗號，用 `split(',')` 會切錯，要做括號配對），再依卡片內寬與各元素字級推算
數字寬度與內容總高，逐一比對是否溢出或撐破。算出來的東西要寫明是算的，不是看到的。

**截圖不要帶視窗尺寸參數。** 用瀏覽器驅動截圖時，若在截圖指令上再指定一次寬高，
它會先縮放視窗再拍，而畫面往往還沒重繪完，拍出來是一整張白的——同一輪連續兩次都這樣，
而 DOM 量測明明抓得到四張門卡與正確數字。正確做法是在**載入時**就把尺寸設好，
截圖時什麼都不要帶。拍出白畫面時先別急著懷疑產出：
`dist/index.html` 的內容用 node 剝掉標籤讀一次就知道是不是真的壞了。

（2026-09-13 的四尺寸表已被本節前半的 09-14 實測表取代，不在這裡重複一份舊值。）

左右兩欄的頂端與底端在桌機尺寸都對齊。這件事**沒有寫進 `check-layout.mjs`**，
只能靠看截圖：先前為了消除門卡內部的空洞，把中段列高改成 `auto auto` 搭配
`align-content`，量測全過，截圖卻看得出左欄浮在中段（置中）或左下空 138px（靠上）
——右欄的清單一路排到底，左欄沒有，一眼就不對稱。
最後回到 `1fr 1fr`：取消 `margin-top:auto` 之後卡片內容本來就置中，撐滿列高只是留白變多。
（這裡原本寫「實測 `alignTopDiff` 與 `doorsBottomVsHotBottom` 皆為 0」，
但檢查器裡從來沒有這兩個值——是對稱這件事本來就得用眼睛看，量測值代替不了。）

規則：

- **快額滿的列不可壓縮**（`flex:0 0 auto`），但**顯示幾列不由斷點決定**。
  每列高度取決於 base 字級（`.hot li a` 的 `min-height:1.9em` 加 1px 框線），
  字級一改，寫死的列數就全錯——2026-09-14 base 從 18.4px 調到 24px，每列 37→47px，
  1440×900 實測 11 列需要 513px 而容器只有 344px，清單被裁掉四成。
  改用 `max-height: round(down, 100%, var(--row-h))`：容器高度對齊列高的整數倍，
  多出來的列被裁在列與列的邊界上，不會出現半列，也不需要任何斷點。
  `--row-h` 由字級推導（`calc(1.9 * var(--fs-base) + 1px)`），**不可以寫死**：
  先前寫 47px（真實值 46.6px），八列就累積 3.2px 誤差，第九列露出一條 3px 的半截。
  為了讓 `100%` 有明確參照，`.hot` 必須是 grid（`auto auto 1fr`）而不是 flex。
- **門卡不可被壓到比內容小**：中段是 `minmax(0,1fr)`，視窗一矮就會把卡片壓扁、
  內容溢出格子去撞底部。矮視窗改為讓卡片內容**連續縮小**（行高、gap、padding、數字上限
  全部綁 vh），縮不動時（≤720px）讓說明文字整行退場，再不夠（≤660px）就改為可捲。
  手機則讓三段（`.ask`／`.doors`／`.foot`）依內容高度排列。
  （手機版原本還寫了 `grid-auto-rows:minmax(150px,auto)` 當門卡下限，但 `.doors` 有顯式的
  `grid-template-rows:1fr 1fr`，隱式列規則不會套用，390×844 實測卡片 134px——
  下限從未生效，已移除。）
- **grid 欄寬一律寫 `minmax(0,1fr)`，不可以只寫 `1fr`。** `1fr` 的最小值是 `auto`，
  擋不住內容把欄位撐開：320px 實測 `.doors` 兩欄的 min-content 是 327.5px，而 `.home`
  扣掉 padding 只剩 284px，結果外層欄寬被撐成 327.5px，三個區塊一起溢出、整頁橫捲。
- 底部標籤數由 `max-width` 斷點決定（1200/1040/560/420px）；≤900px 解除底部清單的
  高度上限，`全部 N 縣市 →` 接在清單後面而不另佔一行（佔一行會把底部撐高、壓縮中段）。
  **可捲模式下不要再設 `.foot ul` 的高度上限**——那條上限是為滿版一頁壓縮底部而存在的，
  頁面可捲之後就沒有理由再裁，而且它會依順序蓋掉 `max-width:900px` 的解除規則
  （320×568 實測把兩行標籤的 66px 壓進 1.6em＝32px）。

量測過程修掉三處裁切：快額滿每列被壓成 18px（內容需 23px，八列全被切字）、
底部「全部 21 縣市 →」連結被 `max-height` 切掉、手機寬度下底部標籤仍被切。

## 8. 還缺什麼

- **座標**：**19,671/33,315（59.0%）有座標**，場館 1,782/2,444。2026-09-13 收到 TGOS
  第一批結果並回填：3,146 筆送出、2,953 筆拿到座標，直接解開 5,026 條邊，另有 400 條走
  「名錄沒座標時回頭查 geocoded」那條路補上。回填前只有 21.5%。
  舊的預估留在這裡對照：當初估回來後到 40.6%、上限 66%，實際落在 59.4%。

  回來後可直接解開 469 門課，另有 195 門課的場館對到無座標的名錄（`registry` 分支會回頭
  查 `geocoded.csv`，所以那批也吃得到）。待送清單裡有 2,219 個門牌目前還沒有課掛著——
  那是學校名錄剛接進來的備料，將來對上就直接有座標。

  送件前先修了 `build_tgos_input.py` 的 `clean_address()`，因為第一批 338 筆查無座標裡
  有一大半是**送件端自己沒清乾淨**、再送一次也會再失敗一次，白耗每日額度。加了五條規則：
  行政區後面的部門字樣（「北投區**校本部**北投區中山路5之12號」）、縣市簡稱重複
  （「中山區**北市**中山區吉林路110號」）、行政區整個重複（「士林區**士林區**承德路4段177號」）、
  與行政區同名的園區（「官田區**官田工業區**工業路40號」）、據點名用連字號接在門牌前
  （「○○分館**--**臺北市北投區立農街1段366號」，前後縣市還會互相矛盾，取後段才是門牌所在）。
  共修好 25 種、442 筆 L1。

  **改送件端的正規化一定要拿 git 裡的舊版並排跑一次 `geocoded.csv` 全部 2,953 筆做回歸。**
  我第一版就誤傷了兩筆：`[區鄉鎮市]` 後面拔「中市」時把「雲林縣西螺鎮**中市路**31號」
  拆成「西螺鎮路31號」（中市路是真實路名），而那個門牌本來已經編碼成功；
  園區規則的 `{0,4}` 貪婪匹配則把「臺中市**西屯區**工業區一路100號」的行政區整個吃掉
  （工業區一路也是真實路名）。加了負向前瞻與「同名才拔」之後，最終回歸結果是
  已成功的 2,953 筆**改動 0 筆**。`norm_address()` 是管線索引鍵的移植、一個字都不能動，
  能改的只有送件用的 `clean_address()`——改了索引鍵不變，回填仍對得回去。

  剩下的 30.0% 多半是連地址都沒有的（只有場地名或完全沒地點），要等座標或名錄補上。

  桃園與臺南聯網的列表層）。

  **回填後一定要用「各縣市座標中位數」抽驗，不能只看覆蓋率數字。** 第一次回填完
  覆蓋率漂亮地跳到 59.4%、三個檢查器全過，但澎湖縣 186 門課的座標中位數離澎湖 183 公里
  （落在臺東外海）。總數完全看不出這種錯誤，因為錯位的座標仍然是合法的臺灣座標。

  查下去是兩個缺陷疊加，兩個都在管線這邊，不是 TGOS 的問題（TGOS 回傳的門牌與座標
  全部正確，換算也對）：

  1. 場館的**名稱比對沒有限制縣市**，臺東的課因此掛進澎湖社大這個場館。
  2. 補座標時用**課程自己的地址**去查快取，而場館的身分來自名錄——兩者是不同地方時，
     就把課程所在地的座標寫進了名錄場館。澎湖社大掛的 183 門課裡有 83 門的地址是
     「臺東市中華路1段684號」，於是整個場館連同全部課程被標到臺東。

  修法：名稱比對加同縣市條件；補座標改用**名錄自己的門牌**（`prev.address`）查快取。
  修完跨縣市比對 283 → 0、座標落在錯誤縣市的場館 12 → 4（影響 5 門課，全是來源把
  地址寫成別縣市的髒資料），澎湖中位數偏離 183 公里 → 1 公里。有座標的場館反而從
  1,672 增加到 1,744——用名錄自己的門牌查，比用課程地址查更準。

  掉到 2,911）；用 `split(',')` 手工解析帶 BOM 的 CSV，導致查表全部落空還以為快取是空的；

  那批，送出字串根本沒有縣市可比。
